# Lakebase Search

Use Lakebase Search to keep semantic, keyword, and hybrid search in Lakebase Postgres. Preserve the user's language,
database driver, framework, and embedding provider; the search layer is SQL and is not tied to a particular model
vendor or SDK.

Lakebase Search requires Postgres 16 or later. Enable only the extensions the task needs:

```sql
CREATE EXTENSION IF NOT EXISTS lakebase_vector CASCADE;
CREATE EXTENSION IF NOT EXISTS lakebase_text;
```

`lakebase_vector` installs `pgvector` through `CASCADE`. `lakebase_text` has no extension dependency. Both rely on
preloaded libraries that Neon enables by default; if the project customized its preloaded-library list, confirm the
relevant library remains enabled.

## Choose the Retrieval Mode

| Need | Mode |
| --- | --- |
| Meaning or paraphrases | Semantic search with `lakebase_ann` from extension `lakebase_vector` |
| Exact terms | Full-text search with BM25 ranking using `lakebase_bm25` from extension `lakebase_text` |
| Semantic and lexical matches | Hybrid search combining vector and BM25 results |

Read the guide for the selected mode:

- [Vector search](references/vector-search.md)
- [Full-text search](references/full-text-search.md)
- [Hybrid search](references/hybrid-search.md)

Use one mode when it clearly matches the product requirement. Use hybrid search when users can express the same
intent through either natural-language meaning or specific vocabulary.

## Shared Data Model

A table can support all three modes:

```sql
CREATE TABLE documents (
  id        bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title     text NOT NULL,
  body      text NOT NULL,
  embedding vector(1536),
  body_tsv  tsvector GENERATED ALWAYS AS
    (to_tsvector('english', body)) STORED
);
```

Replace `1536` with the chosen embedding model's dimension. Generate stored-document and query embeddings with the
same model and preprocessing. Use the PostgreSQL text-search configuration appropriate for the content instead of
assuming `'english'` for every corpus.

Create the vector index with a metric that matches the model.

```sql
CREATE INDEX documents_embedding_ann ON documents
  USING lakebase_ann (embedding vector_cosine_ops);

-- Insert the initial document corpus before this statement.
CREATE INDEX documents_body_bm25 ON documents
  USING lakebase_bm25 (body_tsv)
  WITH (default_limit = 20);
```

After a large bulk load into an existing BM25 index, run `VACUUM` so corpus statistics and scores stay accurate.

## Implementation Rules

- Keep embedding generation outside SQL unless the user's architecture already provides an in-database embedding
  function. Accept vectors from any provider whose dimensions and metric match the schema and index.
- Parameterize query text, vectors, filters, and limits through the existing database driver. Do not introduce a new
  language, SDK, ORM, or model provider solely for search.
- Keep top-K candidate limits explicit. For BM25, align `lakebase_bm25.default_limit` with the query's `LIMIT`; for
  hybrid search, fetch a wider candidate set from each retriever before fusion.
- Apply session settings and their query on the same connection. With a pool or a driver where statements may use
  different connections, put `SET LOCAL` and the search query in one transaction.
- Compare retrieval quality as well as latency on representative queries. Semantic distance, negative BM25 score,
  and fusion scores have different scales and meanings; never combine raw vector and BM25 scores directly without a
  deliberate normalization strategy.
